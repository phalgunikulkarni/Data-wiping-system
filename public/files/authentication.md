# DataGuard local authentication

DataGuard accounts are stored locally in SQLite at the operating system's application-data location (`QStandardPaths::AppDataLocation/dataguard.sqlite3`). The database is created on first launch, retained across launches, and versioned with SQLite `PRAGMA user_version`. Schema initialization runs transactionally and enables foreign-key enforcement.

The initial schema contains `users` and `user_preferences`. Usernames and normalized email addresses are unique case-insensitively. Preferences reference users with `ON DELETE CASCADE`. Future `scans`, `operations`, `audit_events`, and `certificates` should each include a `user_id` foreign key to `users`; those tables are intentionally not created until their associated features are implemented.

Passwords are stored as salted PBKDF2-HMAC-SHA-256 hashes generated by the Windows CNG BCrypt provider, using a fresh 128-bit system-random salt and 600,000 iterations. Verification compares derived hashes in constant time. Argon2id is not currently configured in this Qt/MinGW project; PBKDF2 is the available maintained platform primitive. A future migration may adopt a maintained Argon2id library if that dependency is added and packaged safely.

Registration validates username, email, and password policy in the service layer, inserts through prepared statements, and creates preferences in the same transaction. Sign-in accepts username or email and returns a generic error for invalid credentials. The in-memory signed-in identity is cleared on sign-out. No password or persistent session token is saved. The disabled password-recovery text is deliberate: local email-based password reset is not implemented.

This is local authentication for a single installation. It is not online registration, cloud identity, multi-device synchronization, or a production account-security system. The SQLite database is protected by the operating system account's normal file permissions; it is not encrypted at rest.
